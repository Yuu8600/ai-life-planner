# AI Life Planner 現行実装リファレンス

**基準は調査開始時にリモートmainと照合した `49261d0a96a90d4d31ef0eb6e53f25df05052d03`（PR #27統合後）。** 調査期間は2026年11月26〜27日（日本時間）。Git管理下の実装を静的に読んだ仕様であり、稼働中のサービスの監査記録ではない。

Nativeではログインすると「今日」が開く。利用者は使える時間を選び、候補をチェックして完了を記録するか、「あとで」でその日だけ見送る。名前だけでタスクを登録でき、見積もり・目標・期限は後から補える。想定する利用者は、日常の予定の合間に目標につながる次の一歩を決めたい人（要件と画面からの**推測**）。予定は読取状況に応じて判断材料に使う。「AI相談」は任意で、通常の推薦・順位決めは端末内の決定的な処理。相談からデータを変えるには提案カード上の操作が必要である。

同じリポジトリには三つの体験がある。① Nativeの日常用の推薦・相談、② 設定から自分で開いて案を保存するNativeの高度な時間割、③ サンプル時計とメモリ内データで従来の計画作成を体験するWeb Demo。時間割の作業枠と推薦の日別実施記録は別系統。Webのスクリーンショットや旧PlannerのテストだけからNativeの日常操作を判断できない。

## 1. 画面と到達経路

Expo Routerの画面ファイルは **10件**。Nativeの操作画面は9件と振り分け専用の起点1件。Webは入口を含む7種類の操作画面を同じ10 URLへ割り当てる。下表のURLが単位で、グループ・レイアウト・HTMLシェル、モーダル、同一URL内のモードは件数に含めない。Webの別実装は同じURLの列に併記した。「ログイン中」は復元済みのNativeセッションがあることを指す。

| URL               | Nativeの目的・入口・主なデータ                                                                                                      | Webでの解決先                                       |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| /                 | 起動・認証復元を待ち、sessionで今日／ログインへRedirect。待機画面に入力はない。                                                     | サンプルの入口 DemoWelcomeScreen                    |
| /login            | 未認証でメールとパスワードを扱うAuthScreen。成功・復元後は認証グループを離れる。                                                    | / へリダイレクト                                    |
| /today            | 今日タブ。プロフィール暦日のTask・step・日別結果・方針・直近予定から今の候補を選ぶ。                                                | 保存計画のタイムライン TodayScreen                  |
| /tasks            | タスクタブ。本人のタスク全件、Goal候補、当日結果。追加・編集・完了済みの操作、Goal・step・AIへの入口。                              | 従来のフィルター付きサンプルTasksScreen             |
| /calendar         | 予定タブ。選んだ日の端末・固定予定を一覧、追加・削除・対象日相談。                                                                  | サンプル予定と空き時間 CalendarScreen               |

| /settings         | 今日・予定等 → 設定。本人のプロフィール、アカウント、時間割設定と管理入口。                                                         | サンプルプロフィールとデモ説明                      |

## 2. 画面別の操作表

1行を1操作群とし、同じコールバックの選択肢、開閉、同型の繰り返し行、ラベルの状態差をまとめた。実際のボタン表示数はデータで変わる。「N」「対象名」などは動的な件数・タイトル。「確認」は画面文言・コードコメントまたは世代別設計資料で目的を確認できた箇所、「推測」は挙動からの解釈、「不明」は固有の採用理由が記録されていない箇所。操作結果の列には実装で確認できる挙動を記す。共通操作は各シートにも適用する。Webの確認はwindow.confirmを通るため、表の「キャンセル／削除」等は論理上の選択肢で、ボタンの字面はブラウザに従う。Webのモーダルは背景クリックで閉じられ、Escapeは最前面のものだけを対象にする。通常の一覧でスワイプ削除するハンドラは見つからない。再表示時、DBの値は読み戻される。画面内stateはアンマウントで初期化されるが、タブ切替だけではマウントが続く場合がある。

## 3. 推薦・CRUD・カレンダーの処理

### 「今日」の候補を決める手順

1. **今日を確定する。** フォーカス時とアプリがactiveに戻った時にプロフィールを読み、時間帯を正規化する。フォーカス中は20秒ごとに現在時刻を更新する。プロフィールの暦日が変わると取得キーも変わり、前日のsnapshotは新しい日の候補に使わない。日付が変わっても利用時間はユーザー別に維持する。未保存、不正な値、以前の15分は既定の指定なし。負担はnormalで開始する。今日、タスク、stepで共用する。[useV25Date.ts](../src/navigation/routes/useV25Date.ts)・[V25DailyRoutes.tsx](../src/navigation/routes/V25DailyRoutes.tsx)
2. **材料を集める。** Task全件、全step、当日から90日前まで（両端を含む）の日別結果、Goalの名前を並列取得。Goal名の取得失敗時は空の対応表を使う。方針と予定は別に取得し、取得できた材料で再計算する。stepと結果の取得は500行単位。[TodayRecommendationsScreen.tsx](../src/features/recommendations/TodayRecommendationsScreen.tsx)・[SupabaseRecommendationRepository.ts](../src/services/supabase/repositories/SupabaseRecommendationRepository.ts)
3. **対象を絞る。** completed/skippedのTaskは除外。単発で期限が過ぎたら期限見直しリストへ。毎日は曜日制約なし、weekdays・旧weeklyは当日のISO曜日（月1〜日7）が含まれる日だけ。親Taskの当日結果があれば子も含めて見せない。子は未完了で当日結果がないもの。同じ親の子だけを完了／見送りした時は、別の子や親自身が次の代表候補になり得る。期限はdeadline_local優先、なければdeadlineをプロフィール時間帯に換算する。[recommend.ts](../src/features/recommendations/recommend.ts)
4. **親ごとに一つ選ぶ。** 各子を比較してから親自身を末尾に加える。①既知分数で予定間隔・指定時間の両方に収まる、②既知分数で指定時間内、③分数不明、④今日・明日期限の親本体、の順で最初の一つ。指定なしは時間上限なし。既知分数で長すぎる通常候補は分割導線の候補。未設定を仮の30分に換算しない。予定間隔は適合を優先する材料で、予定中でも推薦を全件ブロックしない。[recommend.ts](../src/features/recommendations/recommend.ts)
5. **並べる。** 比較順は緊急フラグ → 緊急なら期限日 → 方針の重み（対象Task/Goal優先2、15分以下が短時間優先の対象なら1、他0）→ 予定内に収まるか → 分数既知 → 重要度 高・中・低 → 期限昇順（なしは末尾）→ 最終完了日昇順（未実施は空値）→ 作成時刻 → ID → 種別。先頭は比較順のまま。初めの選抜では緊急区分・方針重み・予定適合が先頭と同じ候補のうち未登場Goalを優先し、最初の4件後は残りを順に付ける。単純な期限順または所要時間順ではない。[recommend.ts](../src/features/recommendations/recommend.ts)
6. **画面に並べ直す。** 先に全候補を初期4件で切り、通常を「今から何する？」、緊急を「期限が近いタスク」に振り分ける。lighter_day適用時は初期上限が2と緊急件数の大きい方。「もっと見る」は8件ずつ。指定時間より長い期限例外も表示できる。表示限度と全件の順位・カードの位置を混同しない。条件変更は表示数を戻す。activeで開始日≦今日≦終了日の方針だけが効く。同じ種類＋Task ID＋Goal IDはmanual優先、次に新しい作成時刻、最後にIDで1件採用する。manualを新規作成する一般UIは確認できない。[TodayRecommendationsScreen.tsx](../src/features/recommendations/TodayRecommendationsScreen.tsx)・[policy.ts](../src/features/recommendations/policy.ts)

**日別結果からの復元。** 完了・見送りは `record_recommendation_result` がユーザー単位のトランザクションロック下で既存の同一（本人、日、kind、target）結果を先に返す。新規時はDB側のプロフィール暦日・親と子の所有者／状態を検証する。単発Taskだけ本体statusをcompletedにし、元のstatusも記録する。単発stepだけcompleted_atを設定する。繰り返しはその日の行だけが増える。親の状態に子の件数を自動集計しない。undoは当日の期待結果と照合して当該行を消し、対象本体を復元。古い完了Taskに当日行がなければreopenでpendingに戻す。過去の記録を一緒に消さない。画面の実行ロック、戻り値による即時反映、再読込で通信結果に合わせる。一括は全件成功またはロールバック。[20261118120000_v25_undo_daily_result.sql](../supabase/migrations/20261118120000_v25_undo_daily_result.sql)・[20261123100000_v27_batch_task_actions.sql](../supabase/migrations/20261123100000_v27_batch_task_actions.sql)

### Task・Goalの保存と再表示

- **Task** はユーザーIDで絞り作成時刻降順で取得する。フォームの所要時間空欄はnull。リポジトリは型、所有者、日付、優先度・状態などをデコード時にも検証する。同じ入力の作成結果が不確かな場合、リポジトリインスタンス内で未確認のUUIDを保持し、次の作成で照合・読戻しする。これはアプリを再起動しても続くキューではない。成功行を一覧の先頭に追加、更新は同じIDの置換、削除は除去。タスクのフォーカス時は日付リビジョンで別画面からの変更も取得する。[SupabaseTaskRepository.ts](../src/services/supabase/repositories/SupabaseTaskRepository.ts)・[useTasks.ts](../src/features/tasks/useTasks.ts)・[V2TasksRoute.tsx](../src/navigation/routes/V2TasksRoute.tsx)
- **Goal** はタイトル・任意説明・暦日期限・priority・statusを本人に紐付ける。作成時current_value・target_value・unitはnull、通常編集ではこれらを上書きしない。Goal削除時、Taskは残りgoal_idのみnull。Goalを優先する方針は外部キーの連動削除対象。Goal編集・一覧の更新はuseGoals経由。Native GoalsRouteにはタスク画面と同じフォーカス再取得トークンはなく、同画面のCRUDの結果とリポジトリの切替・再読込に依存する。[GoalsScreen.tsx](../src/features/goals/GoalsScreen.tsx)・[useGoals.ts](../src/features/goals/useGoals.ts)・[SupabaseGoalRepository.ts](../src/services/supabase/repositories/SupabaseGoalRepository.ts)
- **Step** は親Task必須。名称、任意分数、負担、再利用可否、完了日時を持つ。手動追加・編集は返却行を反映、削除後はIDで除去、実施変更後は子一覧と当日結果を再取得。親削除で子は消え、日別結果は当時の名称で閲覧できる。名前だけのクイック追加、通常フォームのTask、AI作成Taskで許容する分数に差がある。[ActionStepsScreen.tsx](../src/features/recommendations/ActionStepsScreen.tsx)・[tasks/validation.ts](../src/features/tasks/validation.ts)・[DraftEditor.tsx](../src/features/ai-chat/v2/DraftEditor.tsx)

### 高度な時間割の生成と保存

`loadDay` は設定、Task、近傍の予定（計画日の前後2日）、履歴（90日前〜6日後）、該当日の保存済み計画を読む。DB入力の指紋を取得前後で比較し、端末予定は別にrevisionを作る。保存済みなら当時の窓とTZを利用。限定モードなしで端末取得不可なら新規配置を抑止する。権限拒否でも完了・スキップ・固定解除の扱いは別。[dayService.ts](../src/features/planner/v2/dayService.ts)・[SupabaseDailyPlanningRepository.ts](../src/services/supabase/repositories/SupabaseDailyPlanningRepository.ts)

`createDailyPlan` は残り時間の柔軟な生活予定を終了・ID順で配置し、残りの約1/4（最低60分、残量が上限）を自由時間に確保。残りに期限・優先度・Task/Goalの実施履歴等で並べたTaskを配置する。分数不明・対象外曜日・期限超過に理由を持たせる。緊急Taskには初回最大2枠、その後は入る限り追加配置する場合がある。異なるTask間の余裕、手動移動時の固定、既存実行枠を尊重する。`moveByPixels` は長押しドラッグを5分単位に丸める。完了・あとで（deferred）・取りやめは作業枠の状態であり、推薦の日別結果RPCは呼ばない。[planner/v2/engine.ts](../src/features/planner/v2/engine.ts)・[timelineEntries.ts](../src/features/planner/v2/timelineEntries.ts)

`approvePlan` はDB・端末を再読込し、保存版・入力指紋・カレンダーの変化、プレビュー再計算結果、開始済み枠等を検証する。SQLの `v2_save_plan` もユーザー、版、サーバー側の指紋、時刻、固定・保護対象等を検証する。再計画・更新はV2のJSON状態を保存し、V1のdaily_plansを置き換えない。[20261114090000_v2_planner.sql](../supabase/migrations/20261114090000_v2_planner.sql)

## 4. AI通信・承認・予算

**通常送信の順序。** ChatScreen → ChatRepository.send → 認証付きv2-chat POST → 本人の文脈取得 → DBで費用予約 → Responses API → 応答を検査 → 費用確定・会話／下書き保存 → 画面が会話と予算を再取得。Task等が変わるのは、これに続くカードの承認RPCが成功した時である。モデルにDBアクセス権や任意の書込ツールを与える経路はない。[ChatScreen.tsx](../src/features/ai-chat/v2/ChatScreen.tsx)・[SupabaseChatRepository.ts](../src/services/supabase/repositories/SupabaseChatRepository.ts)・[functions/v2-chat/index.ts](../supabase/functions/v2-chat/index.ts)

| 境界           | 現行の契約                                                                                                                                                                                                                                                                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 認証・可否     | GET/POSTのみ。BearerをAuthのuserエンドポイントで照合。通常のコンテキスト取得はユーザートークン＋公開鍵、予算予約・確定のみサーバー側の権限。GETは月、configured、calendarSharing、remainingMicrosを返す。モデルを呼ばない。                                                                                                                                    |
| 入力・文脈     | 本文最大12,000バイト、相談文1〜1000字、実在日・UUID検証。直近メッセージ最大6件・各500字、対象Task/Goalまたは最近の候補を絞り、優先度・期限・見積・繰り返し・関連・更新版などを渡す。通常検索はGoal12・Task16行から関連度で4・5件、下書きの親を含め各最大8件。会話の全履歴とは異なる。dayの取得元は現行で空配列、sessions欄があっても予定全体を自動取得しない。 |
| モデル         | サーバー設定名は `V2_OPENAI_MODEL`、`V2_OPENAI_API_KEY`、`V2_OPENAI_INPUT_USD_PER_MILLION`、`V2_OPENAI_OUTPUT_USD_PER_MILLION`。モデル名は固定しない。モデル・鍵と入出力の正の単価が必要。Responsesのjson_object、inputにもJSONの出力指示、max_output_tokens=900、store=false、モデル通信25秒、Supabase内部通信10秒のタイムアウト。                            |
| 予算           | 本人・UTC月に500,000マイクロUSD（0.50 USD）。命令＋JSON入力のUTF-8バイト数に1024を加え24,000を超えれば拒否。予約額はそのバイト数×入力単価＋900×出力単価の切り上げ。DBが本人単位でロック、直近2分のpendingも排他。実測トークン両方が返れば実費推定で確定、取れない場合の月集計は予約額を使う。表示額はアプリの推定値。請求アカウント全体の上限ではない。        |
| 返答・提案     | 提案なしは文章。提案は通常最大8、focus付き最大5。構造・参照ID・日付・分数・曜日・パッチを検査し不正項目を落とす。有効項目ありなら固定の案内文とカード、不正項目だけなら再相談案内。通常回答の一部の実行済み表現も置換する。                                                                                                                                    |
| 変更可能な範囲 | Task作成、既存Taskの項目差分、既存親にstepを作成、期間付き方針。Taskフォーカスでは新規Taskを抑止。Goalフォーカスは関連Taskまたは方針に限定。Goal画面の「小さな行動」は常にstepレコード作成を意味しない。GoalのCRUD、Task削除／完了、カレンダー変更はモデルの許可種別に含まない。                                                                               |
| 表示と履歴     | 一覧はthread作成日の降順。最新メッセージ100件を時系列に返し、古いページはcreated_atとidをカーソルにする。下書きは同じ会話から別クエリで取得。assistant返答の時刻と下書き作成時刻から直前の回答を求めてカードを配置する。対応回答がページ外なら先頭。会話の削除・改名UIは未実装。                                                                               |
| 承認の整合性   | 未編集はv2_approve_draft、選択項目を編集した時はv27_approve_edited_draftが版付き編集と選択承認を1トランザクションで実施。既存Taskへの変更は対象ID・更新版・所有を検査し、before値と適用版をレシートに記録。取り消しは適用後の版が一致する時のみ。閉じた下書きは再適用しない。方針の解除とTask編集取消は異なる操作。                                            |
| 失敗と再試行   | 未設定、予算不足、処理中、認証、サイズ、上流設定／quota／レート／タイムアウト／形式／出力上限／拒否／通信をコード化する。未知コードは汎用接続エラー。上流の本文を画面にそのまま出さず許可された診断項目を記録。通常相談は予約時にuserメッセージを保存するため、モデル失敗でも発言だけ残り得る。クライアントは失敗時も会話・残予算を更新し、入力を保持する。    |

**予定を共有する1回の送信。** 参照情報で「有無」ならbool、詳細なら選択した名称・開始・終了・任意の場所のみ。端末ID、メモ、参加者やアプリ内の固定予定はこの共有対象に含めない。端末で事前確認し、サーバーでも形式・日付の交差を検証して信頼しない参考データとして送る。共有元の読み取り権限と、送信ボタンでの同意は独立。送信先での保持条件はコードから未確認。[CalendarShareEditor.tsx](../src/features/ai-chat/v2/CalendarShareEditor.tsx)・[V2ChatRoute.tsx](../src/navigation/routes/V2ChatRoute.tsx)

新規会話なら汎用名「予定の相談」の枠を作る。相談文を予約RPCに保存せず、正常終了を示す固定マーカーと空の項目配列で確定する。UIは返却された一時回答と方針候補をメモリに保持し、会話切替・アンマウントで消える。既存の通常メッセージは引き続き履歴にある。承認すると `v27_approve_calendar_policies` が成功済みリクエスト・本人・会話・有効対象を照合し、種類、対象ID、期間から固定タイトルの下書きと適用済み方針を生成する。モデルの自由記述・予定名はこのRPCの引数に含めない。却下なら一時候補を破棄。使用量・成功結果・会話枠や承認済み方針まで消えるという意味ではない。[20261118130000_v26_ai_calendar.sql](../supabase/migrations/20261118130000_v26_ai_calendar.sql)・[20261122100000_v27_calendar_policy_approval.sql](../supabase/migrations/20261122100000_v27_calendar_policy_approval.sql)

### 操作回数を比較するための起点

次は読み込み済み・有効な入力・エラーなしの場合の例。テキスト入力とOSのキーボード操作は回数に含めない。

- 「今日」の候補を完了するにはチェック1回。見送るには「あとで」1回。直後なら通知の「元に戻す」1回で取り消せる。後から見送りだけを戻す場合は一覧展開と「戻す」の2回。
- 「タスク」から既存Taskに子行動を手動追加するには、タスク名 →「小さな行動を見る・追加する」→「小さな行動を追加」→ 入力後「保存」の4回。「今日」の分割導線から入ると、親ID・分数を引き継いで追加シートを直接開く。
- 共有なしの新規相談は一覧で本文を入力して「送信」1回。全選択の提案をそのまま採用するならカード上の「追加」または「適用」がもう1回。予定の詳細を共有する場合は対象日・端末での事前取得・予定選択・必要なら場所の同意が加わる。
- 「今日」から初めて時間割を保存するには、「設定」→「時間割を開く」→「時間割の案を見る」→「この変更を保存」の4回。端末取得不可なら許可確認または当日限定モードの選択も必要。
