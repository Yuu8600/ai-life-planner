# AI Life Planner V2.6 — カレンダー連携 × AI承認付き変更提案 実装仕様

- 作成日: 2026-11-18
- ステータス: **採用方針を固定した実装仕様／V2.5ローカル実装との最終照合はCodexが必須**
- ベース: `feat/v2-5-recommendation-first`（報告済み最新ローカルコミット `093cdd2`。その後のコミット・未コミット変更を必ず先に確認）
- 目的: 「予定を踏まえた行動推薦」と「AIとの会話から承認付きでTask・推薦条件が変わる体験」を、V2.5のシンプルなUIを保って実現する。

## 0. 確定したプロダクト境界

1. **予定の詳細をAIへ共有可能**。ただし、端末カレンダーの読取許可と、外部OpenAI APIへの送信同意は別。送信する対象・項目をユーザーが送信前に確認・選択する。デフォルトは送信なし。詳細の共有は選択可能とし、毎回確認できる。予定のタイトルと日時を詳細項目とし、場所の送信は別の明示選択とする。参加者・メモ・URL・プライベート属性等は初期スコープ外。
2. **推薦方針の変更は期間限定**。対象は「今日」「明日」「今週」または開始・終了日を指定した短期間（初期上限14日）。開始・終了はユーザー設定TZのローカル日付。期限後は自動的に推薦へ反映しなくなる。いつでも解除できる。
3. **AIが承認を求めて実行できる操作は、推薦方針の変更・Task作成・Task編集のみ**。Action Step（小さな行動）作成は既存Task作成の関連ワークフローとして許可。AIが直接Goalを作成・編集・削除、Task削除、Task完了・見送り、カレンダーへの書込み・削除・変更、時刻配置の確定、無承認保存を行うことは禁止。相談・要約・振り返りなど読取のみの回答は承認不要。
4. 毎日のTask推薦は**ルールベース**が主体で、OpenAI API停止・予算超過・カレンダー拒否でもTask表示・追加・完了は使える。
5. AIによる変更案は**事前表示・個別編集/選択・明示承認・競合再検証・冪等適用・結果表示・可能な取り消し**が必要。

## 1. ユーザー体験／完了条件

### 1.1 価値が伝わる1分デモ

1. iPhoneカレンダーに講義13:00–15:00、アルバイト18:00–21:00がある。
2. 「今日」に予定の概要と、期限・重要度・予定との適合を考慮したTask候補が表示される。予定未登録時間を実際の自由時間と断定しない。
3. AI相談で「今週はレポート優先。今日は疲れたのでTOEICは軽めに」と送る。必要なら選んだ予定の詳細を送信プレビューで確認・共有する。
4. AIは「今週末までレポートの優先度を推薦内で上げる」「今日は短時間Taskを優先」という**期間付きの推薦方針案**を示す。Task本体のpriorityは変更しない。
5. 承認するとTodayの候補と理由が変わり、コンパクトな「適用中」表示から元に戻せる。
6. 「レポートを小さく分けて」にはTask/Action Stepの追加案が出て、選択承認後だけ保存される。

### 1.2 合格基準

- AI相談で共有しない選択の場合、カレンダー詳細がOpenAIへ送信されない。
- 共有内容のプレビューには選択した日時・予定名・（選択した場合のみ）場所が表示される。
- 承認前・却下時にTask/推薦方針が変化しない。
- 承認後にTodayへ戻ると適用中の推薦方針と**根拠のある推薦理由**が見える。
- 期間終了後は自動で通常推薦へ戻り、ユーザーは手動解除もできる。
- 既存のTask作成・完了/取り消し・繰り返しTask・Action Step・V1/V2履歴・高度なPlannerを壊さない。

## 3. UI構成（4タブ維持）

### 今日（Today）
- 「直近の予定」1〜3件（予定名をアプリ内表示するのは端末権限があれば可）、今日のおすすめ3〜5件、必要なら「もっと見る」。
- カレンダー上の次の予定と「予定のない区間」を**参考情報**として表示。時間がない・短い場合でも推薦自体を止めない。
- 「今日の余裕」設定とTask完了チェック（再タップで未完了）、今日の見送り／解除をその場で操作できる。
- 承認済みの推薦方針が有効なら、「今週はレポート優先中［解除］」など1行の表示。複数なら短い要約と「詳細」。
- 推薦理由は例「明日が期限」「優先設定中」「カレンダー上では次の予定まで40分」。未推定の所要時間・空き時間を事実として断定しない。
- 「AIに相談」はチャットへ遷移。Todayに長いチャットを埋め込まない。

### タスク
- 名前だけで作成、期限/重要度/Goal/繰り返し/時間は任意。編集フォームを増殖させない。
- Task行の「AIに小さく分けてもらう」から、既存Stepドラフト承認を呼ぶ。Task編集のAI案も既存フォーム/承認に統合。
- 既存の完了↔未完了、繰り返しTaskの当日実施記録、削除確認を維持。

### 予定
- 端末カレンダー予定の表示、日付/時間軸切替の従来機能を尊重。
- 「AIにこの日の予定を相談」でAI画面に遷移し、対象日をプリセット。**遷移だけでは外部送信しない**。
- AIによる端末カレンダーの編集は行わない。

### AI相談
- 従来の会話一覧/履歴/自然文入力を維持。新規会話に毎回タイトル入力を要求しない方向で改善（既存の破壊的置換はしない）。
- 送信欄付近に「参照情報」入口。カレンダー共有は「なし（初期）／予定あり・なしの要約／選択した予定の詳細」の選択。詳細では対象日・イベント、送信するタイトル/日時、任意の場所を送信直前にプレビュー。送信ボタンを押したそのリクエストにのみ有効。
- AI変更案は会話内の**一種類の統一カード**にまとめる。対象、変更前→変更後、適用期間、影響（Task本体の変更か、推薦のみか）を表示し、個別選択/編集 → 承認/却下を用意。別途複数のDraft管理画面を作らない。
- 保存成功時に「適用しました」「今日で確認」または「Taskを見る」。却下後・失敗後も会話を継続できる。

## 4. カレンダー情報の送信／プライバシー

1. OSの端末カレンダー読取権限だけではAI APIへの送信を許可したとみなさない。
2. **「予定の詳細も共有可能」という利用者の選択を実装する**。ユーザーが選んだ期間・予定だけを対象にする。
3. 送信レベル: `none`（既定） / `availability_summary` / `selected_event_details`。詳細は `startAt,endAt,title` と、`includeLocation=true` のときの `location` に限定。メモ・説明・参加者・連絡先・カレンダーID・端末固有ID等は送らない。終日予定・非公開イベントには適切な注意と除外選択肢を示す。
4. 詳細は**実際に外部送信するデータのプレビュー**を用意。共有する予定ごとに選択解除できる。UIで「OpenAI APIに送信されます」とわかる言葉を使用。
5. `selected_event_details` を選んでも、次の別のAI送信に無断で詳細を引き継がない。保存するなら表示用の選択状態だけ。無期限の包括的送信同意として扱わない。
6. 端末予定はDBへ恒久的に複製しない。Edge Functionへ一時送信した内容もDB・開発ログ・エラーログ・分析イベントに記録しない。**会話本文や回答・ログに詳細が混入して永続化されないよう**、既存チャット保存処理とレスポンスの扱いを監査する。会話上の返答にイベント詳細が含まれる場合は、履歴に残ることをユーザーに告知するか、詳細を保存しない設計にする。削除導線も明示する。
7. 通信は認証済みEdge Function経由。APIキーはサーバー側のみ。許可なし・取得失敗時にはTask推薦・チャットのカレンダー抜き相談が動く。
8. AIへの入力に外部カレンダー由来の指示文が混ざっても**信頼できないデータ**として扱う。予定のタイトル/場所/詳細を指示として実行しない。サーバーでもペイロードサイズ・件数・対象日数を制限する。

## 5. 推薦エンジンへの予定連携（AI呼出し不要）

- 既存V2.5エンジンを拡張し、カレンダーのbusy時間帯（端末ローカル処理）、現在時刻、ユーザーの余裕、Task/Stepの既存見積もり、期限、優先度、完了/見送り、承認済み一時方針を入力する。
- 予定の重複は統合し、終日予定・非公開予定・予定状態を正しく扱う。予定をすべて登録していない可能性があるため「空いている」と断定せず「カレンダー上では予定なし」と記す。
- 所要時間が分かるTask/Stepは、候補時間との適合を考慮する。所要時間未登録は厳密に適合判定せず、短く着手するなどの提案を示す。移動・準備時間を勝手に仮定しない。
- 順位の土台は**期限 → 重要度 → 実行状況**。承認済み方針はその上に限定的な重み/優先度を与えるが、当日・翌日期限などの緊急Taskを黙って隠さない。表示を切り替えた理由を説明できる決定的ルールにする。
- カレンダー未許可/取得失敗時はV2.5ルール推薦にフォールバックし、「予定を確認できないためTask情報で推薦」と短く表示。今日とTask画面のロードが失敗しない。
- 同じ日の推薦は、Task追加・更新・完了・見送り・カレンダー変更・承認/解除された方針など**意味のある入力変更時だけ**再評価し、頻繁な不必要シャッフルを避ける。

## 6. 期間限定推薦方針

### 6.1 許可する操作（ホワイトリスト）

- `focus_goal`: 指定された既存Goalに紐づくTaskを、その期間だけ優先（Goal自体は変更しない）。
- `focus_task`: 指定された既存Taskを、その期間だけ優先（Taskの恒久 `priority` を変更しない）。
- `prefer_short`: 指定された期間だけ短いTask/Stepを優先（未知の作業時間は短いと断定しない）。対象のGoal/Taskを任意で絞れる。
- `lighter_day`: 指定日だけおすすめの表示数/負荷を抑える。ただし期限近い重要Taskを気づかないうちに隠さない（警告・別枠表示）。

初期版ではこれ以外のルール文字列や任意コードをAIから受け入れない。実行エンジンの優先順位をAIが直接数値で指定しない。

### 6.2 データ概念（既存スキーマに合わせる）

```ts
type RecommendationPolicy = {
  id: string;
  userId: string;
  startDate: string; // YYYY-MM-DD, user planning timezone
  endDate: string;   // inclusive
  kind: 'focus_goal' | 'focus_task' | 'prefer_short' | 'lighter_day';
  targetGoalId?: string | null;
  targetTaskId?: string | null;
  source: 'ai' | 'manual';
  sourceDraftId?: string | null;
  status: 'active' | 'revoked';
  revision: number;
};
```

- `endDate >= startDate`、期間14日以内、ユーザーが所有するGoal/Taskだけを受け入れる。日付は対象ユーザーTZのLocalDateとして評価。「今週」は月曜〜日曜、「今日」は当日。TZ変更時の過去データは別日付へ勝手に書き換えない。
- Todayの評価で `startDate <= today <= endDate && status==='active'` の方針だけを適用。期限切れレコードは履歴として残せるが、適用されない。
- 同じ期間のルールが重なった場合は、手動の明示操作・期限緊急性を優先し、同一対象・種類では最新の有効ルールを採る等の決定的な競合規則を定義する。画面からどの方針が効いているか確認できる。
- ユーザー解除は`revoked`として保存（誤操作時の戻しを可能にする）。承認した変更は元データのTask priorityに作用しない。
- 新規テーブルが必要ならRLS、GRANT、user_id/対象IDの所有権検査、ユーザー別インデックス、冪等キー/一意制約、日付のCHECK制約を付け、他ユーザーを参照できないようにする。**V2.5で同等の仕組みがあれば再利用**。

## 7. AIが生成できる変更案の契約

許可するトップレベル種別は3つのみ：

```ts
type AllowedAiChange =
  | { type: 'create_task'; requestId: string; draft: TaskCreateDraft }
  | { type: 'update_task'; taskId: string; expectedRevision: string; patch: TaskEditablePatch }
  | { type: 'set_recommendation_policy'; policy: RecommendationPolicyDraft };
```

- `TaskCreateDraft` は名前必須、期限・重要度・Goal・繰り返し・見積時間は任意。小さな行動は既存のAction Step作成下書き・親Task参照を再利用する。親Taskを勝手に完了しない。
- `TaskEditablePatch` はタイトル、期限、重要度、所要時間、関連Goal、繰り返しのうち明示した項目のみ変更。**Task status/completion/deletionや任意DB列の変更不可**。
- `RecommendationPolicyDraft` は第6節のホワイトリスト、対象ID・期間などを含む。
- AI生成JSONはサーバーとクライアントでスキーマ検証する。モデル出力の対象ID・user_id・日付・権限・既存値を信用しない。空/不正案は安全に却下し、会話は継続可能。
- 提案カードは対象、変更前→変更後、期間、Task本体の変更か推薦のみかを表示。複数案は**個別選択承認**。承認時にはサーバーがDBの現況/所有者/revisionを再確認し、競合時は勝手に上書きせず案を更新する。
- 同じ下書きの承認再送でTask/Policyが二重作成されないよう、安定したIDまたは冪等キーとDB一意制約を使う。部分失敗時の状態も正しく表示する。可能なら一括選択は一つのトランザクションとする。
- Task更新を取り消す場合は「承認時点の変更前値」を保存し、それ以降に別の編集があれば無条件ロールバックしない。期限付きPolicyはTodayから解除できる。Task作成は即時の取り消し/アーカイブを安全に案内し、既存の通常削除確認を維持。

## 8. セキュリティ・費用・互換性

- 既存のOpenAI月額予算約$0.50相当、予約・使用量記録・上限到達時のフォールバックを維持。AIを使わない推薦にAPI通信を発生させない。実API呼出しはQAでも明示許可なく実施しない。
- Supabase Auth・RLSを基盤とし、Edge Functionがユーザー権限を無視して任意Taskを書き換えない。安全なRPC/トランザクションで変更を確定。
- ログにSecrets、認証トークン、予定詳細、完全なAIプロンプトを残さない。個人データ送信の同意を説明できるUIとする。
- `tasks.estimated_minutes` のNULL可・V2.5既存Step/履歴・旧V1/V2の履歴を維持。ローカルQA(旧V2 `55321`、V2.5 `56421`と報告)を取り違えない。production migrationや本番Secrets変更は禁止。QA migrationsは元に戻す手順とともにローカルの分離環境で検証する。
- Calendar取得/AI失敗時もTask一覧と推薦が壊れない。タイムゾーン境界、日跨ぎ、繰り返し、終日予定に注意。

## 9. 最小限の検証

### Codex側の自動テスト

- 既存V2.5重要テスト・型チェック・lint・iOS simulator build（環境可能なもの）。
- Policyの当日/今週/期間外/解除/TZ境界/重複優先の純粋関数テスト。
- 緊急Taskが一時方針によって不可視にならないこと。
- カレンダー許可なし・詳細送信同意なし・予定未取得でAI送信ペイロードに詳細を含めないこと。
- 詳細共有の選択イベント以外の除外・場所を選択しない場合の除外・サイズ上限・プロンプトインジェクション対策。
- Task作成/編集、Action Step作成、Policy保存における本人所有、競合検知、冪等承認、RLS、二重送信。
- API予算超過/AI機能無効時に通常のTask・推薦が動くこと。

### ユーザーが行う手動QA

1. 権限なし: Today・Task・推薦が利用可能。
2. 読取許可: 端末予定の概要がTodayに表示され、推薦の根拠に利用される。
3. AI相談でカレンダー共有なし: 会話できるが、詳細の外部送信はゼロ。
4. 予定の詳細共有: 送信プレビューで対象を選び、送信したイベントだけを参考に回答。場所は独立選択。
5. 「今週はレポート優先」: 推薦Policy案→承認→Today反映→解除→通常に復帰。
6. 「タスクの期限を変えて」: 変更前後を表示→承認後保存→別画面で再取得。
7. 古い提案の承認や二度押し: 競合・重複なし。
8. AI未設定・予算上限・通信失敗: Task機能は利用可能。
9. 再起動・日跨ぎ・翌週: 有効期間と解除状態が再現され、期限切れPolicyは無効。
10. VoiceOver、大きい文字、画面下部キーボード、通常サイズiPhoneのUI確認。

### 受け入れ条件（ポートフォリオ視点）

- **カレンダー → 推薦 → AI相談 → 変更案の承認 → Today反映・解除**を1〜2分でデモできる。
- ユーザーは「AIが何を参照し、何を変更するか」を事前に理解できる。
- 自然文の相談だけで済む場合はDBを更新しない。
- 週限定方針が終了したら元の推薦方針へ自動で戻る。変更したTaskの実データは勝手に元へ戻さない（恒久編集と区別）。

## 10. 実装順と成果物

1. **現状監査・保護**: `git status`, 現行ブランチ/HEAD/未コミット/未push確認。実コードと`docs/v2_5`、既存RPC/Edge Function/型を読み、重複やDB互換を調査。現在ブランチを保護して新しいローカル作業ブランチを作る（例 `feat/v2-6-ai-calendar-integration`）。作業中の変更を上書きしない。
2. **端末予定の読取と推薦連携**: カレンダー取得の共通read model、任意取得エラー時のfallback、既存推薦エンジンの拡張。AI呼出しを必須化しない。
3. **AIコンテキスト共有**: 選択・送信プレビュー、データ最小化、Edge Functionペイロード境界、保存/ログ漏れ監査。
4. **期間限定Policy**: 型・保存・RLS・期限判定・解除・推薦順位との接続。
5. **AI変更案と統一カード**: 既存draft/approvalフローをTask作成・編集・Policyに統合。多重書込み・競合・Undo/解除を検証。
6. **UI・QA**: 4タブの主目的を守って最小限の画面変更、主要テスト、Simulator起動（実操作できない項目は未検証）、手動QA手順作成。

成果物: `docs/v2_6/EXISTING_FEATURE_AUDIT.md`、`DESIGN_DECISIONS.md`、`IMPLEMENTATION_NOTES.md`、`MANUAL_QA.md`。必要なSQL migration、重要自動テスト、ローカルコミット。GitHubへのpush・PR作成・マージ・リリース・タグ公開はユーザーのみ。**完了時にユーザーがpush/PRすべきタイミングを明示**。

## 11. 非対象

- AIによるGoal作成/編集/削除、Task削除/完了処理、カレンダー書込み・予定変更、無承認操作、AIによる毎回の推薦順位計算、全Task自動時刻配置、詳細な作業時間監視、複雑な自律エージェント。
- 既存のGoal作成AI下書きが残っている場合はデータを削除せず、今回の統一AI操作メニューから外す。既存の会話履歴や保存済み下書きを破壊しない。
- 大規模なUI新タブ追加、Goal/Taskの別体系、V1/V2保存データの強制移行。

## 12. 既知の未確認事項と扱い

- **V2.5実装はユーザーのCodex報告による把握**。当該ローカルブランチ・未pushコミット・`docs/v2_5/*` は、この仕様作成環境から直接取得できていない。既存のschema/table/functionの正式名はCodexに検査させ、既存データモデルに合わせて実装する。
- 最新UI/UX改善がV2.5ブランチに反映済みかをCodexが確認。未統合の別作業ブランチがあれば独断で履歴を書き換えず、内容の矛盾を報告する。
- 詳細カレンダーを含む会話の保存方針は要注意。**個人情報の無断永続化を避ける**ことを最優先とし、履歴に詳細を保存する場合はユーザーへの明示と削除導線を整える。
