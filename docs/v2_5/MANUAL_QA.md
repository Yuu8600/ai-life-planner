# V2.5の手動QA

本番と分けたSupabaseとテスト用アカウントで実施する。旧版を残す場合はV2.5のアプリ識別子も分ける。[互換性の詳細](IMPLEMENTATION_NOTES.md)

## 接続先の確認

このMacのV2.5用Simulatorアプリは **AI Life Planner V2.5 QA**（`com.uyu.ailifeplanner.v25qa`）。接続先は `http://127.0.0.1:56421`。旧V2用の `55321` は所要時間が必須なので、V2.5で名前だけのタスクを送ると `23502` で保存を拒否される。開発ビルドで試す場合は、起動時に検証用URLとpublishable keyを指定する。

保存結果を確認できない旨が表示された場合は、タスク一覧を再読み込みして追加済みか確認する。同じ画面で入力を変えずに再試行する場合は、最初の保存IDを再利用する。

## ローカル起動

1. feat/v2-5-recommendation-first をチェックアウトし、DockerとXcodeのSimulatorを起動する。既存の検証環境を使う場合は接続先を確認する。
2. 新規に用意する場合は別ディレクトリにプロジェクトを作り、検証用Supabaseを起動する。56421〜56429が使用中の場合は別の空きポートを選ぶ。

   ```sh
   qa_dir=$(mktemp -d /tmp/ai-life-planner-v25.XXXXXX)
   mkdir -p "$qa_dir/supabase"
   cp -R supabase/migrations supabase/functions "$qa_dir/supabase/"
   cp supabase/seed.sql "$qa_dir/supabase/"
   sed -e 's/ai-life-planner"/ai-life-planner-v25-qa"/' \
     -e 's/5432/5642/g' -e 's/5433/5643/g' supabase/config.toml > "$qa_dir/supabase/config.toml"
   supabase --workdir "$qa_dir" start -x studio,storage-api,realtime,imgproxy,logflare,vector,supavisor
   supabase --workdir "$qa_dir" status
   ```

3. アプリに検証環境の API URL と publishable key を設定する。iOS SimulatorのURLは http://127.0.0.1:56421。実機では端末からアクセスできる検証環境のURLを使う。AI無しで試す場合は検証環境でAIキーを設定しない。
4. Simulator用QAビルドを使う場合は、ビルド時と同じ検証DBを起動し、下記のパスを成果物の場所に置き換えて実行する。既存の開発ビルドを使う場合はローカルURLと publishable key を設定してMetroを起動する。

   ```sh
   xcrun simctl install booted /path/to/AILifePlanner.app
   xcrun simctl launch booted com.uyu.ailifeplanner.v25qa
   ```

5. テストアカウントでログインする。確認メールが必要なら分離環境のMailpit（既定では http://127.0.0.1:56424）を開く。

## 完了と見送りの取り消し

1. 「今日」で単発タスクのチェックを付ける。「実行履歴」に移ることを確認し、アプリを終了・再起動する。同じ項目のチェックを外すと候補に戻り、タスクタブでも未完了になる。
2. 別の候補を「見送る」で移動し、直後は「元に戻す」、後からは「実行履歴」の「今日の見送り」から「取り消す」。候補に戻り、実行履歴から当日の見送りが消える。再起動してもその状態が続く。
3. 繰り返しタスクをチェックする。タスクタブの「完了済み」に「今日の実施済み」と表示される。チェックを外すと当日分だけ消えることを確認する。過去日の履歴と曜日は残る。
4. タスク名をタップし、状態欄や「詳細設定」を開く操作がなく、名前だけで保存できることを確認する。曜日を2日選ぶと「週2回」が表示される。「タスクを削除」を押し、確認でキャンセルすると一覧に残る。
5. 期限が明日の90分タスクと15分のタスクを作る。「15分」を選んでも、明日が期限のタスクも所要時間の目安付きで表示される。

## 試用後の公開作業

公開する場合は本番と旧クライアントの切り替え手順を決める。Codexが対象作業ブランチをpushし、main向けPRを作成してCI・差分・レビューを確認し、[現行のGit運用](../development.md#git--github運用)の条件を満たしたらマージする。通常のpush・PR・マージに個別許可は不要。DB反映とEdge Functionの更新はPRとは別に扱う。
